## 43. What are isolation levels and why do they matter?

### Answer

**Isolation levels** define how much one database transaction can see or be affected by other **concurrent transactions**.

They matter because multiple users or application requests can access and modify the same data at the same time.

For example, imagine two transactions operating on the same account:

```text
Transaction A          Transaction B
     ↓                      ↓
  Read balance           Read balance
     ↓                      ↓
  Update balance         Update balance
```

Without proper concurrency control, their operations could interfere and produce incorrect results.

The SQL standard defines four main isolation levels:

1. **Read Uncommitted**
2. **Read Committed**
3. **Repeatable Read**
4. **Serializable**

---

## 1. Read Uncommitted

This provides the weakest isolation.

A transaction may be allowed to read changes made by another transaction **before that transaction commits**.

This can result in a **dirty read**.

Example:

```text
Transaction A              Transaction B

Update balance → 500
                           Read balance → 500
Rollback
```

Transaction B read `500`, but Transaction A eventually rolled back, so `500` was never committed.

### Problem

**Dirty read** — reading data that another transaction has not committed.

This level is uncommon when correctness is important, and some databases do not actually provide true dirty reads even if the SQL standard defines the level.

---

## 2. Read Committed

A transaction can only see **committed data** from other transactions.

Example:

```text
Transaction A              Transaction B

Update balance → 500
                           Cannot see 500 yet

COMMIT
                           Can now see 500
```

This prevents dirty reads.

However, the same query or transaction can potentially see different committed values at different times if another transaction commits a change between the reads.

This is called a **non-repeatable read**.

`READ COMMITTED` is the default isolation level in PostgreSQL.

---

## 3. Repeatable Read

This provides stronger isolation.

Once a transaction reads a row, repeated reads within that transaction are protected from certain changes made by concurrent transactions.

Conceptually:

```text
Transaction A              Transaction B

Read balance → 100

                           Update balance → 200
                           COMMIT

Read balance → 100
```

Transaction A continues to see its transactionally consistent view rather than suddenly seeing `200`.

The exact behavior, especially around concurrent updates and **phantom rows**, varies by database implementation.

---

## 4. Serializable

`SERIALIZABLE` provides the strongest standard isolation level.

The goal is to make concurrent transactions behave as though they had executed **one at a time in some serial order**, while still allowing the database to use concurrency internally.

For example:

```text
Transaction A
     ↓
Transaction B
```

The database ensures that the final result is equivalent to some valid serial ordering.

The trade-off is that stronger isolation can reduce concurrency and may cause transactions to fail with serialization errors, requiring the application to retry them.

---

## Common Problems

Isolation levels are usually discussed in terms of anomalies such as:

### Dirty Read

Reading uncommitted data from another transaction.

```text
A: UPDATE → 500
B: READ → 500
A: ROLLBACK
```

B read data that never committed.

---

### Non-Repeatable Read

Reading the same row twice and getting different committed values because another transaction changed it between the reads.

```text
A: READ → 100

B: UPDATE → 200
B: COMMIT

A: READ → 200
```

---

### Phantom Read

Running the same query twice and seeing a different **set of matching rows** because another transaction inserted or deleted rows that satisfy the query.

```text
A: SELECT ... WHERE salary > 50000
   → 5 rows

B: INSERT employee with salary 60000
B: COMMIT

A: SELECT ... WHERE salary > 50000
   → 6 rows
```

The additional row is a **phantom**.

---

## Comparison

| Isolation Level  | Dirty Reads | Non-repeatable Reads | Phantom Reads*               |
| ---------------- | ----------- | -------------------- | ---------------------------- |
| Read Uncommitted | Possible    | Possible             | Possible                     |
| Read Committed   | Prevented   | Possible             | Possible                     |
| Repeatable Read  | Prevented   | Prevented            | Depends on DB implementation |
| Serializable     | Prevented   | Prevented            | Prevented                    |

*The SQL-standard definitions and actual behavior can differ across database systems, especially for `REPEATABLE READ`.

---

## Why Do Isolation Levels Matter?

There is a trade-off between **consistency and concurrency**.

Higher isolation generally provides stronger guarantees, but may increase:

* locking or synchronization overhead
* contention
* transaction failures/retries
* reduced concurrency

So you don't simply choose the strongest level for every application.

For example:

```text
Simple read-heavy operation
        ↓
READ COMMITTED may be sufficient

Critical concurrent operation
        ↓
May require stronger isolation
```

The correct choice depends on the application's consistency requirements and the database's concurrency model.

### Interview Takeaway

Remember:

> **Isolation level determines how transactions interact with concurrent transactions and what changes they can observe.**

The four standard levels are:

```text
READ UNCOMMITTED
        ↓
READ COMMITTED
        ↓
REPEATABLE READ
        ↓
SERIALIZABLE
```

As a general mental model, moving upward gives **stronger isolation guarantees but potentially less concurrency**.

A strong interview answer should also mention that **the exact behavior is database-specific**, so you should know the defaults and implementation details of the database you're usin
