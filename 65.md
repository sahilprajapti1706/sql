
## 65. How would you handle missing or duplicate records using SQL?

### Answer

When preparing data, especially for **analytics or ML training**, I would handle:

1. **Missing values** → identify and decide whether to replace, exclude, or keep them.
2. **Duplicate records** → identify duplicates and decide which record should be retained.

---

## 1. Handling missing values

### Find NULL values

```sql
SELECT *
FROM customers
WHERE email IS NULL;
```

Use `IS NULL`, not:

```sql
WHERE email = NULL;
```

because `NULL` represents an unknown/missing value.

### Replace NULL with a default value

Use `COALESCE()`:

```sql
SELECT
    customer_id,
    COALESCE(phone, 'Not Available') AS phone
FROM customers;
```

For numeric data:

```sql
SELECT
    customer_id,
    COALESCE(age, 0) AS age
FROM customers;
```

However, `0` is not always an appropriate replacement. For ML or analytics, the correct treatment depends on what the missing value means.

### Calculate averages while ignoring NULLs

Most SQL aggregate functions such as `AVG()` ignore `NULL` values:

```sql
SELECT AVG(salary)
FROM employees;
```

If salaries are:

```text
50000
60000
NULL
70000
```

the average is calculated from the three non-NULL salaries.

---

## 2. Handling duplicate records

First, identify duplicates.

For example, if `email` should be unique:

```sql
SELECT
    email,
    COUNT(*) AS duplicate_count
FROM customers
GROUP BY email
HAVING COUNT(*) > 1;
```

To find the actual duplicate rows:

```sql
SELECT *
FROM customers
WHERE email IN (
    SELECT email
    FROM customers
    GROUP BY email
    HAVING COUNT(*) > 1
);
```

---

## 3. Identify which duplicate record to keep

`ROW_NUMBER()` is useful when we need to select one record and identify the remaining duplicates.

```sql
WITH ranked AS (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY email
            ORDER BY created_at DESC
        ) AS rn
    FROM customers
)
SELECT *
FROM ranked
WHERE rn = 1;
```

Here, the **most recently created record** is kept.

The duplicate records are:

```sql
SELECT *
FROM ranked
WHERE rn > 1;
```

The rule for deciding which record to keep should come from the business requirement—for example, newest record, verified record, or record with the most complete information.

---

## 4. Prevent duplicates in the first place

For fields that must be unique, enforce the rule at the database level:

```sql
ALTER TABLE customers
ADD CONSTRAINT unique_customer_email
UNIQUE (email);
```

This is better than relying only on application code.

For example:

```text
Application validation → helpful
Database UNIQUE constraint → actual database guarantee
```

---

## 5. Handling duplicate rows during JOINs

Duplicates can also be created by an incorrect JOIN.

For example:

```text
1 customer
5 orders
3 payments
```

Joining both one-to-many tables directly can potentially produce:

```text
5 × 3 = 15 rows
```

instead of the expected customer-level record.

A safer approach is often to aggregate first:

```sql
WITH order_summary AS (
    SELECT
        customer_id,
        COUNT(*) AS order_count,
        SUM(amount) AS total_spent
    FROM orders
    GROUP BY customer_id
)
SELECT
    c.customer_id,
    c.name,
    COALESCE(o.order_count, 0) AS order_count,
    COALESCE(o.total_spent, 0) AS total_spent
FROM customers c
LEFT JOIN order_summary o
    ON o.customer_id = c.customer_id;
```

This is particularly important when creating **ML training datasets**, because accidental duplicate rows can distort the model.

---

## 6. `DISTINCT` is not always the solution

You can remove completely identical result rows with:

```sql
SELECT DISTINCT *
FROM customers;
```

But `DISTINCT` should not blindly be used to solve duplicate-data problems.

If two rows have the same email but different IDs:

```text
1 | Rahul | rahul@gmail.com
5 | Rahul | rahul@gmail.com
```

they are not identical rows, so `DISTINCT` will **not** tell you which one should be kept.

For this situation, use a business rule with `ROW_NUMBER()`.

---

### Interview Takeaway

A good interview answer is:

> **First identify the type of missing or duplicate data. For missing values, use `IS NULL` to detect them and `COALESCE()` when an appropriate replacement is needed. For duplicates, use `GROUP BY ... HAVING COUNT(*) > 1` to identify them and `ROW_NUMBER()` to select which record to retain. For prevention, use database constraints such as `NOT NULL` and `UNIQUE`. When joins create duplicates, check relationship cardinality and aggregate one-to-many data before joining.**

The important distinction is:

```text
Missing data
    → IS NULL / COALESCE()

Duplicate data
    → GROUP BY + HAVING
    → ROW_NUMBER() for deduplication

Prevent future duplicates
    → UNIQUE constraint
```
