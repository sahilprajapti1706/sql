
## 51. What is normalization? Explain 1NF, 2NF, and 3NF

### Answer

**Normalization** is the process of organizing data in a relational database to:

* Reduce unnecessary data duplication
* Prevent data inconsistencies
* Avoid insertion, update, and deletion anomalies
* Make relationships between data clearer

The basic idea is:

> **Store each piece of information in the appropriate place and connect related data using keys.**

Normalization is usually discussed in **normal forms**, such as 1NF, 2NF, and 3NF.

---

## 1. First Normal Form (1NF)

A table is in **1NF** when:

1. Each column contains **atomic values** rather than multiple values in one cell.
2. There are no repeating groups of columns.
3. Each row represents a distinct record.

### ❌ Not in 1NF

```text
students
+----+--------+-------------------------+
| id | name   | phone_numbers            |
+----+--------+-------------------------+
| 1  | Rahul  | 9876..., 8765...        |
| 2  | Amit   | 9123...                 |
+----+--------+-------------------------+
```

`phone_numbers` contains multiple values.

### ✅ 1NF

```text
students
+----+--------+------------+
| id | name   | phone      |
+----+--------+------------+
| 1  | Rahul  | 9876...    |
| 1  | Rahul  | 8765...    |
| 2  | Amit   | 9123...    |
+----+--------+------------+
```

Or, in a real application, phones could be moved to a separate table:

```text
students
+----+-------+
| id | name  |
+----+-------+
| 1  | Rahul |
| 2  | Amit  |
+----+-------+

student_phones
+----+------------+
| student_id | phone |
+----+------------+
| 1          | 9876... |
| 1          | 8765... |
| 2          | 9123... |
+----+------------+
```

### Key idea

**1NF = one logical value per cell.**

---

# 2. Second Normal Form (2NF)

A table is in **2NF** when:

1. It is already in **1NF**.
2. Every non-key column depends on the **entire primary key**, not just part of it.

This mainly matters when the table has a **composite primary key**.

### Example

Suppose:

```text
enrollments
+------------+-----------+--------------+-------------+
| student_id | course_id | student_name | course_name |
+------------+-----------+--------------+-------------+
| 1          | 101       | Rahul        | SQL         |
| 1          | 102       | Rahul        | Java        |
| 2          | 101       | Amit         | SQL         |
+------------+-----------+--------------+-------------+
```

Primary key:

```text
(student_id, course_id)
```

Now consider the dependencies:

```text
student_id → student_name
course_id  → course_name
```

But:

```text
(student_id, course_id) → student_name
```

is not really needed because `student_name` depends only on `student_id`.

Similarly:

```text
course_id → course_name
```

So we have **partial dependencies**.

### ❌ Problem

`student_name` is repeated for every course the student takes.

If Rahul changes his name, multiple rows need to be updated.

### ✅ Convert to 2NF

Separate the entities:

```text
students
+----+-------+
| id | name  |
+----+-------+
| 1  | Rahul |
| 2  | Amit  |
+----+-------+
```

```text
courses
+-----+------------+
| id  | name       |
+-----+------------+
| 101 | SQL        |
| 102 | Java       |
+-----+------------+
```

```text
enrollments
+------------+-----------+
| student_id | course_id |
+------------+-----------+
| 1          | 101       |
| 1          | 102       |
| 2          | 101       |
+------------+-----------+
```

Now attributes depend on the appropriate key.

### Key idea

**2NF = 1NF + no partial dependency on part of a composite key.**

> If the primary key consists of only one column, partial dependency cannot occur, so a 1NF table with a single-column key is automatically in 2NF.

---

# 3. Third Normal Form (3NF)

A table is in **3NF** when:

1. It is already in **2NF**.
2. Non-key columns do not depend on other non-key columns.

In other words:

> **Non-key attributes should depend on the key, the whole key, and nothing but the key.**

### Example

Consider:

```text
employees
+----+-------+---------------+-------------+
| id | name  | department_id | department  |
+----+-------+---------------+-------------+
| 1  | Rahul | 10            | Engineering|
| 2  | Amit  | 20            | HR          |
| 3  | Priya | 10            | Engineering|
+----+-------+---------------+-------------+
```

Primary key:

```text
id
```

Dependencies:

```text
id → department_id
department_id → department
```

Therefore:

```text
id → department_id → department
```

`department` depends on `department_id`, which is a non-key column.

This is a **transitive dependency**, so the table is not in 3NF.

### ✅ Convert to 3NF

Create a separate department table:

```text
employees
+----+-------+---------------+
| id | name  | department_id |
+----+-------+---------------+
| 1  | Rahul | 10            |
| 2  | Amit  | 20            |
| 3  | Priya | 10            |
+----+-------+---------------+
```

```text
departments
+----+-------------+
| id | name        |
+----+-------------+
| 10 | Engineering |
| 20 | HR          |
+----+-------------+
```

Now:

```text
employees.department_id
        ↓
departments.id
```

The department name is stored in only one place.

### Key idea

**3NF = 2NF + no transitive dependency of non-key attributes.**

---

## Quick Comparison

| Normal Form   | Main Rule                          | Problem It Solves                   |
| ------------- | ---------------------------------- | ----------------------------------- |
| **1NF** | Atomic values, no repeating groups | Multiple values in one cell         |
| **2NF** | No partial dependency              | Dependency on part of composite key |
| **3NF** | No transitive dependency           | Non-key → non-key dependency       |

### Easy Way to Remember

For a table to be properly normalized:

```text
1NF
↓
Atomic values

2NF
↓
Depends on the whole key

3NF
↓
Depends on nothing except the key
```

A common memory phrase is:

> **"The key, the whole key, and nothing but the key."**

This is a useful intuition for 1NF–3NF, although it is a simplification rather than the formal definition of all normalization theory.

---

## Why Normalization Matters in Real Applications

Suppose you store customer information repeatedly in every order:

```text
orders
+--------+-------------+------------+----------+
| order  | customer_id | customer   | phone    |
+--------+-------------+------------+----------+
| 1001   | 5           | Rahul      | 9876...  |
| 1002   | 5           | Rahul      | 9876...  |
| 1003   | 5           | Rahul      | 9876...  |
```

If Rahul changes his phone number, multiple rows must be updated.

A normalized design would use:

```text
customers
    ↓
orders
```

with:

```text
orders.customer_id → customers.id
```

Now customer information has one source of truth.

However, **normalization is not about splitting tables as much as possible**. In real systems, controlled denormalization can sometimes improve read performance or simplify reporting. The correct design depends on the workload and consistency requirements.

### Interview Takeaway

> **Normalization organizes relational data to reduce redundancy and prevent anomalies. 1NF ensures atomic values, 2NF removes partial dependencies on composite keys, and 3NF removes transitive dependencies between non-key attributes.**
