## 26. What is the difference between a subquery and a JOIN?

### Answer

Both **subqueries** and **JOINs** can be used to work with data from multiple tables, but they express the problem differently.

The key idea is:

> **A JOIN combines rows from tables, while a subquery uses the result of one query inside another query.**

---

### 1. JOIN

A `JOIN` combines related rows from two or more tables based on a condition.

Suppose we have:

**employees**

| id | name  | department_id |
| -: | ----- | ------------: |
|  1 | Sahil |            10 |
|  2 | Rahul |            20 |
|  3 | Priya |            10 |

**departments**

| id | name |
| -: | ---- |
| 10 | IT   |
| 20 | HR   |

To get each employee's department:

```sql
SELECT
    e.name,
    d.name AS department
FROM employees e
JOIN departments d
    ON e.department_id = d.id;
```

The JOIN directly combines employee rows with their matching department rows.

---

### 2. Subquery

A subquery places one query inside another query.

For example:

> Find employees who work in the IT department.

```sql
SELECT name
FROM employees
WHERE department_id IN (
    SELECT id
    FROM departments
    WHERE name = 'IT'
);
```

The inner query first identifies the relevant department ID, and the outer query uses that result.

---

## Same Problem, Two Approaches

Many SQL problems can be solved using either.

### Using a JOIN

```sql
SELECT e.name
FROM employees e
JOIN departments d
    ON e.department_id = d.id
WHERE d.name = 'IT';
```

### Using a subquery

```sql
SELECT name
FROM employees
WHERE department_id IN (
    SELECT id
    FROM departments
    WHERE name = 'IT'
);
```

Both can produce the same result.

The choice depends on **what you are trying to express**, readability, and the actual execution plan.

---

## Key Differences

| Feature                             | JOIN                     | Subquery                              |
| ----------------------------------- | ------------------------ | ------------------------------------- |
| Main purpose                        | Combine rows from tables | Use one query's result inside another |
| Combines columns from tables?       | Naturally                | Not necessarily                       |
| Can filter using another query?     | Yes                      | Yes                                   |
| Can express relationships directly? | Yes                      | Yes                                   |
| Can be correlated?                  | No                       | Yes                                   |
| Best thought of as                  | Combining datasets       | Nesting query logic                   |

---

## When should you prefer a JOIN?

Use a `JOIN` when you need **columns from both tables** in the result.

Example:

> "Show employee name and department name."

```sql
SELECT e.name, d.name AS department
FROM employees e
JOIN departments d
    ON e.department_id = d.id;
```

A JOIN is a natural fit because you're combining information from both tables.

---

## When is a subquery useful?

Subqueries are particularly useful when you need to **filter or compare against a calculated/set result**.

For example:

> "Find employees earning more than the company-wide average."

```sql
SELECT name, salary
FROM employees
WHERE salary > (
    SELECT AVG(salary)
    FROM employees
);
```

Here, you don't need columns from another table. You simply need the result of the calculation.

Another common case is `EXISTS`:

```sql
SELECT c.name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

This expresses:

> "Return customers for whom at least one matching order exists."

---

## Important: Don't assume JOIN is always faster

A common interview misconception is:

> "JOINs are always faster than subqueries."

That's not generally true.

Modern databases such as PostgreSQL have optimizers that can transform different SQL formulations into similar execution plans.

For performance-sensitive queries, use:

```sql
EXPLAIN ANALYZE
```

and examine the actual execution plan and performance on your data.

---

## A Simple Decision Rule

Ask yourself:

### "Do I need to combine information from multiple tables?"

➡️ **JOIN is often the natural choice.**

### "Do I need the result of another query to filter, compare, or check something?"

➡️ **A subquery may be a natural choice.**

For example:

```text
Need employee + department information?
        ↓
       JOIN

Need employees earning > average salary?
        ↓
     Subquery

Need customers who have at least one order?
        ↓
   EXISTS subquery
   (or sometimes JOIN)
```

### Interview Takeaway

> **A JOIN combines related rows from tables, while a subquery uses the result of one query inside another query.**

Neither is universally better. **Choose the form that makes the relationship or filtering logic clear, then verify performance with the execution plan when performance matters**

## Answer

A primary key uniquely identifies each row in a table. It cannot contain NULL values and is usually implemented on an `id` column.

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(255) NOT NULL
);
```

### Interview takeaway

Every relational table should have a primary key to guarantee row identity and support relationships.
