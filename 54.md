## 54. How would you design tables for a real application?

### Answer

For a real application, I would **start from the business requirements and relationships**, not from individual tables.

A practical process is:

```text
Requirements
    ↓
Identify entities
    ↓
Identify relationships
    ↓
Define keys and constraints
    ↓
Normalize the schema
    ↓
Add indexes based on query patterns
    ↓
Consider transactions and concurrency
    ↓
Review security, scalability, and future changes
```

Let's use an **e-commerce application** as an example.

---

## 1. Identify the main entities

First, identify the important business objects.

For an e-commerce application:

```text
User
Product
Category
Order
Order Item
Payment
Address
```

These usually become tables.

```text
users
products
categories
orders
order_items
payments
addresses
```

---

## 2. Define the relationships

Next, determine how these entities relate.

```text
User 1 ───── N Orders

Order 1 ───── N Order Items

Product 1 ───── N Order Items

Category 1 ───── N Products

Order 1 ───── N Payments
```

For example:

```text
users
   │
   └──── orders
             │
             └──── order_items
                       │
                       └──── products
```

This tells us where foreign keys should go.

---

## 3. Define primary keys

Each table should have a reliable way to uniquely identify its records.

For example:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE
);
```

The `id` is the primary key.

For most application tables, I would generally prefer a **stable surrogate key** such as an integer/UUID, while keeping business identifiers separately constrained when needed.

---

## 4. Define foreign keys

For the order relationship:

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    order_date TIMESTAMP NOT NULL,

    FOREIGN KEY (user_id)
        REFERENCES users(id)
);
```

This enforces:

> Every order must reference an existing user.

Foreign keys provide database-level referential integrity instead of relying only on application code.

---

## 5. Handle many-to-many relationships correctly

Suppose a product can belong to multiple categories and a category can contain multiple products.

Instead of storing:

```text
product.category_ids = "1,2,5"
```

use a junction table:

```sql
CREATE TABLE product_categories (
    product_id BIGINT NOT NULL,
    category_id BIGINT NOT NULL,

    PRIMARY KEY (product_id, category_id),

    FOREIGN KEY (product_id)
        REFERENCES products(id),

    FOREIGN KEY (category_id)
        REFERENCES categories(id)
);
```

This keeps the relationship relational and queryable.

---

## 6. Normalize first

I would normally start with a **normalized design** to avoid unnecessary duplication.

For example, don't store:

```text
orders
+----+-------------+---------------+
| id | customer_id | customer_name |
+----+-------------+---------------+
```

if the customer's canonical name already belongs in `users`.

Instead:

```text
orders.customer_id → users.id
```

and retrieve the name through a JOIN.

However, normalization isn't an absolute rule. If profiling later shows a specific read path is expensive, controlled denormalization can be considered.

---

## 7. Add constraints

Constraints protect the database from invalid data.

For example:

```sql
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    price NUMERIC(10,2) NOT NULL,
    stock INTEGER NOT NULL DEFAULT 0,

    CHECK (price >= 0),
    CHECK (stock >= 0)
);
```

Useful constraints include:

* `PRIMARY KEY`
* `FOREIGN KEY`
* `NOT NULL`
* `UNIQUE`
* `CHECK`
* `DEFAULT`

The database should enforce important invariants rather than trusting only application validation.

---

## 8. Think about real business rules

This is where real-world schema design differs from a textbook example.

Suppose an order is created for a product costing ₹500.

Later, the product price changes to ₹700.

Should the old order now show ₹700?

Usually, **no**.

Therefore, `order_items` should store the price actually charged:

```sql
CREATE TABLE order_items (
    id BIGINT PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(10,2) NOT NULL,

    CHECK (quantity > 0),
    CHECK (unit_price >= 0),

    FOREIGN KEY (order_id)
        REFERENCES orders(id),

    FOREIGN KEY (product_id)
        REFERENCES products(id)
);
```

Here, `products.price` represents the **current product price**, while `order_items.unit_price` represents the **historical transaction price**.

That's an important real-world design decision.

---

## 9. Design for transactions

Some operations must happen together.

For example, placing an order might involve:

```text
Create order
     ↓
Create order items
     ↓
Reduce inventory
     ↓
Create payment record
```

These operations may need a transaction:

```sql
BEGIN;

-- create order
-- create order items
-- update inventory
-- create payment

COMMIT;
```

If something fails:

```sql
ROLLBACK;
```

The schema should support the application's consistency requirements.

---

## 10. Add indexes based on actual queries

After understanding the application's query patterns, add indexes where they provide value.

For example, if we frequently query:

```sql
SELECT *
FROM orders
WHERE user_id = 101
ORDER BY order_date DESC;
```

a composite index might be appropriate:

```sql
CREATE INDEX idx_orders_user_date
ON orders(user_id, order_date DESC);
```

Don't create indexes on every column.

Indexes improve some reads but increase storage and write-maintenance costs.

---

## 11. Think about NULL carefully

Decide whether a value is genuinely optional.

For example:

```sql
phone VARCHAR(20)
```

might allow `NULL` if a user isn't required to provide a phone number.

But:

```sql
email VARCHAR(255) NOT NULL
```

might be mandatory for an application where every account requires an email.

Don't use `NULL` simply because it's convenient; define what missing data means for the business.

---

## 12. Consider deletion behavior

Foreign keys should have an intentional deletion policy.

For example:

```sql
FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE RESTRICT
```

or potentially:

```sql
ON DELETE CASCADE
```

depending on the business rule.

For historical records such as orders, blindly cascading a user deletion could be dangerous because it may remove important transaction history.

Sometimes **soft deletion** is more appropriate:

```text
deleted_at
```

rather than physically deleting the row.

---

## 13. Think about security

Sensitive data should be designed carefully.

For example:

* Don't store plaintext passwords.
* Store password hashes using an appropriate password-hashing algorithm.
* Restrict database permissions.
* Avoid exposing internal database IDs unnecessarily when a public identifier is more appropriate.
* Encrypt/protect sensitive data where required.
* Use parameterized queries to prevent SQL injection.

Schema design and application security are closely related.

---

## 14. Consider future requirements

I would avoid designing only for today's exact UI.

For example, instead of:

```text
users
home_address
work_address
```

a separate `addresses` table might make more sense if users can have multiple addresses:

```text
users
  │
  └──── addresses
          ├── home
          ├── work
          └── shipping
```

The goal isn't to predict every future requirement, but to avoid obvious designs that make normal changes unnecessarily difficult.

---

A simplified e-commerce schema could look like:

```text
  ├───────────────┐
  ↓               ↓

                  │
                  ↓
             order_items
                  │
                  ↓
               products
                  │
                  ↓
              categories

orders
  │
  ↓

```

With relationships:

```text

Product    1 ─── N OrderItem

Order      1 ─── N Payment
User       1 ─── N Address
```

## A Practical Design Checklist

When designing tables, I would ask:

```text
1. What are the business entities?
2. What does each table represent?
3. What uniquely identifies each row?
4. What are the relationships?
5. Where should the foreign keys live?
6. Which fields are required?
7. Which values must be unique?
8. What CHECK constraints are needed?
9. What does NULL mean for each optional field?
10. What happens when related data is deleted?
11. What queries will the application run frequently?
12. Which indexes support those queries?
13. Which operations need transactions?
14. Is data duplicated unnecessarily?
15. Could any historical data be accidentally changed?
16. Are sensitive fields protected?
```

### Interview Takeaway

> **For a real application, I would start from business requirements, identify entities and relationships, define primary and foreign keys, normalize the schema, add constraints for data integrity, and then design indexes based on actual query patterns. I would also consider transactions, deletion behavior, historical data, security, NULL semantics, and future scalability.**

The important distinction is that **good database design is not just about creating tables**. It is about designing a data model that correctly represents the business while remaining **consistent, queryable, maintainable, and performan**
