## 23. How do you decide which JOIN to use in a real problem?

### Answer

The easiest way to choose a `JOIN` is to ask:

> **"Which rows do I want to keep in the final result?"**

Don't choose a JOIN based only on the table relationship. First understand the **business question** and identify which table's rows must be preserved.

### 1. Start with the requirement

For example:

> "Show only users who have placed an order."

You only need users that have a matching order.

➡️ Use **INNER JOIN**

```sql
SELECT u.name, o.amount
FROM users u
INNER JOIN orders o
    ON u.id = o.user_id;
```

---

### 2. Ask: "Do I need unmatched rows?"

This is the most important decision.

| Requirement                         | JOIN                |
| ----------------------------------- | ------------------- |
| Only matching records               | `INNER JOIN`      |
| Keep every row from the left table  | `LEFT JOIN`       |
| Keep every row from the right table | `RIGHT JOIN`      |
| Keep everything from both tables    | `FULL OUTER JOIN` |
| Every possible combination          | `CROSS JOIN`      |
| Relate rows within the same table   | `SELF JOIN`       |

---

### 3. INNER JOIN — "Only matching records"

Use it when records without a match are **not useful**.

Example:

> "Find customers who have placed orders."

```sql
SELECT c.name, o.id AS order_id
FROM customers c
INNER JOIN orders o
    ON c.id = o.customer_id;
```

Customers without orders disappear from the result.

**Mental model:**

```text
Customers ∩ Orders
       ↓
   Matching only
```

---

### 4. LEFT JOIN — "Keep everything from this table"

Use it when the left table represents the **main population you want to see**, even if there is no matching record.

Example:

> "Show all customers and their orders, including customers who haven't placed any order."

```sql
SELECT
    c.name,
    o.id AS order_id
FROM customers c
LEFT JOIN orders o
    ON c.id = o.customer_id;
```

A customer with no order will still appear:

| name  | order_id |
| ----- | -------: |
| Sahil |      101 |
| Rahul |      102 |
| Priya |     NULL |

This is probably the **most useful JOIN pattern in real applications**.

You can also use it to find missing relationships:

> "Find customers who have never placed an order."

```sql
SELECT c.id, c.name
FROM customers c
LEFT JOIN orders o
    ON c.id = o.customer_id
WHERE o.id IS NULL;
```

---

### 5. RIGHT JOIN — "Keep everything from the right table"

Use it when you specifically want to preserve every row from the **right-side table**.

```sql
SELECT
    c.name,
    o.id AS order_id
FROM customers c
RIGHT JOIN orders o
    ON c.id = o.customer_id;
```

However, in practice, you can usually rewrite it as a `LEFT JOIN` by swapping the tables:

```sql
SELECT
    c.name,
    o.id AS order_id
FROM orders o
LEFT JOIN customers c
    ON c.id = o.customer_id;
```

Because of this, many developers prefer `LEFT JOIN` for readability and consistency.

---

### 6. FULL OUTER JOIN — "Keep everything"

Use it when you need **matching and unmatched records from both sides**.

For example:

> "Compare customers in System A and System B and find records that exist in either system."

```sql
SELECT
    a.customer_id AS system_a_id,
    b.customer_id AS system_b_id
FROM system_a_customers a
FULL OUTER JOIN system_b_customers b
    ON a.customer_id = b.customer_id;
```

This is particularly useful for **data reconciliation and comparison**.

---

### 7. CROSS JOIN — "Give me every combination"

Use it only when you intentionally need a **Cartesian product**.

Example:

> "Generate every combination of product and available color."

```sql
SELECT
    p.name,
    c.color
FROM products p
CROSS JOIN colors c;
```

If there are 10 products and 5 colors:

```text
10 × 5 = 50 combinations
```

Be careful because the result can become extremely large.

---

### 8. SELF JOIN — "Compare rows within the same table"

Use it when rows in the same table have relationships with each other.

Example:

> "Show each employee and their manager."

```sql
SELECT
    e.name AS employee,
    m.name AS manager
FROM employees e
LEFT JOIN employees m
    ON e.manager_id = m.id;
```

Here, the `employees` table is used twice with different aliases.

---

## A practical decision process

When solving a JOIN problem in an interview or real project, think in this order:

### Step 1 — What is the main entity?

For:

> "Show all customers and their orders"

The main entity is `customers`.

### Step 2 — Do I want unmatched main entities?

Yes, because customers without orders should also appear.

➡️ `LEFT JOIN`

### Step 3 — What connects the tables?

```sql
customers.id = orders.customer_id
```

### Step 4 — Write the JOIN

```sql
FROM customers c
LEFT JOIN orders o
    ON c.id = o.customer_id
```

### Step 5 — Check the expected result

Ask yourself:

> "If a customer has no order, should that customer still appear?"

If **yes** → likely `LEFT JOIN`.

If **no** → likely `INNER JOIN`.

---

## Quick Decision Cheat Sheet

```text
Do I need every possible combination?
        │
       YES ──→ CROSS JOIN
        │
       NO
        ↓
Are the two sides the same table?
        │
       YES ──→ SELF JOIN
        │
       NO
        ↓
Do I need unmatched rows?
        │
      NO ──→ INNER JOIN
        │
       YES
        ↓
Which side must always be preserved?
        │
   LEFT ──→ LEFT JOIN
        │
  RIGHT ──→ RIGHT JOIN
        │
  BOTH ──→ FULL OUTER JOIN
```

### Common Interview Trap

Don't decide between `INNER JOIN` and `LEFT JOIN` simply because:

> "There is a foreign key, so I should use INNER JOIN."

A foreign key tells you **how the tables are related**. It does **not** tell you which JOIN the business requirement needs.

For example, the same relationship:

```sql
customers.id = orders.customer_id
```

can use either:

```sql
INNER JOIN
```

or:

```sql
LEFT JOIN
```

depending on whether customers without orders should be included.

### Interview Takeaway

> **Choose a JOIN based on which rows the result must preserve, not simply based on how the tables are related.**

The most important distinction to remember:

**INNER → matching only**
**LEFT → all left + matches**
**RIGHT → all right + matches**
**FULL → everything from both**
**CROSS → every combination**
**SELF → same table joined to itsel**

## Answer

`EXISTS` checks whether a subquery returns at least one row. `IN` checks whether a value is present in a set of values.

```sql
SELECT *
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

### Interview takeaway

`EXISTS` is often better for large subqueries because it can stop early once a match is found.
