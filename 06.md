## 6. What are constraints in SQL?

### Answer

**SQL constraints are rules enforced by the database to control what data can be stored in a table.**

They help maintain **data integrity, consistency, and valid relationships** between tables.

For example, if a user table requires every user to have a unique ID and a non-empty email, constraints allow the database itself to enforce those rules rather than relying only on application code.

---

## Why do we need constraints?

Suppose an application accidentally tries to insert:

```text
id = 101
email = NULL
age = -50
```

Without appropriate constraints, invalid data might enter the database.

Constraints allow the database to reject invalid operations at the **database level**.

This is important because data can be modified by:

* Backend applications
* Admin scripts
* ETL pipelines
* Data-import tools
* Multiple services

The database should not blindly trust every data source.

---

# Common SQL Constraints

The most important constraints are:

1. `PRIMARY KEY`
2. `FOREIGN KEY`
3. `NOT NULL`
4. `UNIQUE`
5. `CHECK`
6. `DEFAULT`

---

## 1. PRIMARY KEY

A `PRIMARY KEY` uniquely identifies each row.

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name VARCHAR(100)
);
```

The database will not allow two rows with the same `id`, and a primary-key value cannot be `NULL`.

Example:

```text
id = 1  → valid
id = 2  → valid
id = 1  → rejected
```

### Purpose

**Entity integrity** — every record has a unique identifier.

---

## 2. FOREIGN KEY

A `FOREIGN KEY` ensures that a value references an existing key in another table, subject to the configured referential actions.

```sql
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    user_id INTEGER,
  
    FOREIGN KEY (user_id)
        REFERENCES users(id)
);
```

If `users.id = 10` does not exist, inserting an order with `user_id = 10` will normally be rejected.

### Purpose

**Referential integrity** — relationships between tables remain valid.

---

## 3. NOT NULL

`NOT NULL` prevents a column from containing `NULL`.

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

This is invalid:

```sql
INSERT INTO users (id, name)
VALUES (1, NULL);
```

The database rejects it because `name` cannot be `NULL`.

### Important distinction

`NULL` does not mean an empty string (`''`) or zero (`0`).

It represents the absence/unknown nature of a value.

---

## 4. UNIQUE

`UNIQUE` ensures that values in a column or column combination are not duplicated, subject to the database's handling of `NULL`.

For example:

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    email VARCHAR(255) UNIQUE
);
```

Two users cannot have the same email value.

```text
sahil@example.com  → valid
rahul@example.com  → valid
sahil@example.com  → rejected
```

A table can have **multiple `UNIQUE` constraints**, unlike a primary-key constraint.

---

## 5. CHECK

`CHECK` ensures that values satisfy a specified condition.

For example:

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    age INTEGER CHECK (age >= 18)
);
```

This is rejected:

```sql
INSERT INTO users (id, age)
VALUES (1, 15);
```

because:

```text
15 >= 18
```

is false.

Another example:

```sql
CHECK (salary > 0)
```

This prevents non-positive salaries.

### Why is CHECK useful?

It puts simple business/data-validity rules close to the data itself instead of relying exclusively on application-level validation.

---

## 6. DEFAULT

`DEFAULT` provides a value when the application does not explicitly provide one.

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    status VARCHAR(20) DEFAULT 'active'
);
```

If we execute:

```sql
INSERT INTO users (id, name)
VALUES (1, 'Sahil');
```

the database can automatically store:

```text
status = 'active'
```

---

# Combining Multiple Constraints

A table can have several constraints at the same time:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    age INTEGER CHECK (age >= 18),
    status VARCHAR(20) DEFAULT 'active'
);
```

Here:

| Column     | Constraint                | Purpose                          |
| ---------- | ------------------------- | -------------------------------- |
| `id`     | `PRIMARY KEY`           | Uniquely identifies the user     |
| `name`   | `NOT NULL`              | User must have a name            |
| `email`  | `UNIQUE` + `NOT NULL` | Email must be present and unique |
| `age`    | `CHECK`                 | Age must satisfy the condition   |
| `status` | `DEFAULT`               | Automatically provides a value   |

---

## Column-level vs Table-level Constraints

Constraints can be written directly with a column:

```sql
email VARCHAR(255) UNIQUE
```

or separately at the table level:

```sql
CREATE TABLE users (
    id INTEGER,
    email VARCHAR(255),

    CONSTRAINT users_pk PRIMARY KEY (id),
    CONSTRAINT users_email_unique UNIQUE (email)
);
```

Table-level definitions are particularly useful for **composite constraints**.

For example:

```sql
CREATE TABLE enrollments (
    student_id INTEGER,
    course_id INTEGER,

    PRIMARY KEY (student_id, course_id)
);
```

Here the combination of `student_id` and `course_id` must be unique.

---

# Constraints vs Application Validation

This is an important practical distinction.

Suppose your frontend checks:

```text
Email must be unique
```

That validation improves user experience, but it is **not sufficient**.

Two requests could arrive at nearly the same time:

```text
Request A → checks email → available
Request B → checks email → available

Request A → inserts
Request B → inserts
```

A database-level `UNIQUE` constraint can enforce the rule reliably.

Therefore:

> **Application validation is useful for user experience, while database constraints provide a final integrity guarantee at the data layer.**

You often want both.

---

## Common Mistakes

### 1. Thinking constraints are only for validation

Constraints do more than validate user input. They also enforce:

* uniqueness
* required values
* relationships
* domain rules
* data integrity

### 2. Assuming `UNIQUE` and `PRIMARY KEY` are identical

Both can enforce uniqueness, but they have different semantics. A table has one primary-key constraint, while it can have multiple unique constraints.

### 3. Using only frontend validation

Frontend validation can be bypassed. Important data-integrity rules should also be enforced by the backend/database where appropriate.

### 4. Confusing `NULL` with an empty value

```text
NULL  → absence/unknown value
''    → empty string
0     → numeric zero
```

They are not equivalent.
