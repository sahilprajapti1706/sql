## 5. What are candidate, composite, and surrogate keys?

### Answer

These are different ways of thinking about how records are uniquely identified in a relational database.

* **Candidate key** → Any minimal set of columns that can uniquely identify a row.
* **Composite key** → A key made from **two or more columns**.
* **Surrogate key** → An artificially generated identifier with no business meaning, such as an auto-incrementing integer or UUID.

A useful mental model:

```text
Candidate Key → Which columns could uniquely identify this row?
Composite Key → What if uniqueness requires multiple columns?
Surrogate Key → What if we create a separate artificial ID?
```

---

## 1. Candidate Key

A **candidate key** is a minimal column or combination of columns that can uniquely identify every row in a table.

Suppose we have:

```text
users
+----+-------------------+------------+
| id | email             | mobile     |
+----+-------------------+------------+
| 1  | sahil@example.com  | 9876543210 |
| 2  | rahul@example.com  | 9123456780 |
+----+-------------------+------------+
```

Suppose both `id` and `email` are guaranteed to be unique.

Then we could have:

```text
id       → Candidate Key
email    → Candidate Key
```

One of these can be selected as the **primary key**.

For example:

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    email VARCHAR(255) UNIQUE
);
```

Here:

* `id` is the **primary key**.
* `email` is another **candidate key** that is enforced as unique.

### Candidate key vs primary key

A table can have **multiple candidate keys**, but one candidate key is chosen as the **primary key**.

```text
Candidate keys:
    ├── id
    └── email
          ↓
One is selected as
Primary Key
```

### Why "minimal" matters

Suppose `(email, mobile)` together uniquely identify a user, but `email` alone is already unique.

Then `(email, mobile)` is **not** a candidate key because it contains an unnecessary attribute.

A candidate key must be **minimal** while still maintaining uniqueness.

---

# 2. Composite Key

A **composite key** is a key consisting of **two or more columns**.

Consider a student enrollment table:

```text
enrollments
+------------+-----------+-------+
| student_id | course_id | grade |
+------------+-----------+-------+
| 101        | CS101     | A     |
| 101        | CS102     | B     |
| 102        | CS101     | A     |
+------------+-----------+-------+
```

A student can enroll in multiple courses, and a course can contain multiple students.

Neither of these alone is unique:

```text
student_id = 101  → appears multiple times
course_id  = CS101 → appears multiple times
```

But their combination can be unique:

```text
(student_id, course_id)
```

We can define:

```sql
CREATE TABLE enrollments (
    student_id INTEGER,
    course_id VARCHAR(20),
    grade CHAR(1),

    PRIMARY KEY (student_id, course_id)
);
```

Here:

```text
(student_id, course_id)
```

is a **composite primary key**.

### Why use a composite key?

It is useful when the **combination of attributes naturally identifies an entity or relationship**.

Common examples include:

* Student + Course
* Product + Warehouse
* User + Role
* Order + Product

---

# 3. Surrogate Key

A **surrogate key** is an artificially generated identifier that has **no business meaning**.

For example:

```text
users
+----+--------+-------------------+
| id | name   | email             |
+----+--------+-------------------+
| 1  | Sahil  | sahil@example.com  |
| 2  | Rahul  | rahul@example.com  |
+----+--------+-------------------+
```

The `id` could simply be generated by the database:

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255) UNIQUE
);
```

The user does not care what `id = 1` means. It is simply an identifier.

Other common surrogate-key formats include:

```text
Auto-increment integer
UUID
Generated bigint
```

### Why use surrogate keys?

They can be useful when the natural/business identifier:

* is long or cumbersome,
* can change,
* consists of multiple columns,
* is not guaranteed to be globally unique,
* or is inconvenient to reference from other tables.

For example, an email address might identify a user today, but an application may allow the email address to change. A generated `user_id` can remain stable.

---

# Natural Key vs Surrogate Key

This distinction often appears in interviews.

Suppose:

```text
users
id = 101
email = sahil@example.com
```

If `email` is used to identify the user, it is a **natural key** because it comes from the application's real-world/business data.

If `id = 101` is generated solely for identification, it is a **surrogate key**.

| Aspect                    | Natural Key                             | Surrogate Key                               |
| ------------------------- | --------------------------------------- | ------------------------------------------- |
| Meaning                   | Has business meaning                    | No business meaning                         |
| Source                    | Real-world/business attribute           | Artificially generated                      |
| Example                   | Email, ISBN, employee number            | Auto-generated ID, UUID                     |
| Can business data change? | Potentially                             | Usually independent of business changes     |
| Typical use               | When a stable natural identifier exists | Common for application/database identifiers |

A surrogate key does **not** mean that the underlying business attributes should lose their uniqueness constraints. For example, you might still keep:

```sql
email VARCHAR(255) UNIQUE
```

even when `id` is the primary key.

---

## How the concepts relate

These terms describe **different properties**, so they are not mutually exclusive.

For example:

```text
id
```

can be:

* a **candidate key** because it uniquely identifies rows,
* the **primary key** because we selected it as the main identifier,
* and a **surrogate key** because it was artificially generated.

Similarly:

```text
(student_id, course_id)
```

can be:

* a **candidate key** because the combination uniquely identifies an enrollment,
* a **composite key** because it contains multiple columns,
* and the **primary key** if we choose it as the table's primary key.

This is an important distinction in interviews: **"candidate", "composite", and "surrogate" describe different aspects of a key.**

---

## Quick Comparison

| Key                     | Main idea                                             | Example                     |
| ----------------------- | ----------------------------------------------------- | --------------------------- |
| **Candidate Key** | Minimal attribute(s) that can uniquely identify a row | `email`                   |
| **Composite Key** | Key containing multiple columns                       | `(student_id, course_id)` |
| **Surrogate Key** | Artificially generated identifier                     | `id = 101` / UUID         |
| **Primary Key**   | Candidate key selected as the table's main identifier | `users.id`                |

### Interview Takeaway

> **A candidate key is any minimal set of attributes that can uniquely identify a row. A composite key contains multiple columns. A surrogate key is an artificial identifier, such as an auto-generated integer or UUID, that has no business meaning.**

One particularly useful interview point is:

**A surrogate key can also be a candidate key and can be selected as the primary key**
