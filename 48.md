## 48. Why can having too many indexes be harmful?

### Answer

Indexes make **read queries faster**, but they are not free. Every index adds **storage and maintenance cost**, especially when data changes.

Think of an index as an additional shortcut the database maintains. More shortcuts can help searching, but every time the underlying data changes, those shortcuts may also need to be updated.

### 1. Slower INSERT operations

When you insert a row, the database may need to update **every relevant index**.

For example:

```sql
INSERT INTO users (name, email, age)
VALUES ('Rahul', 'rahul@example.com', 25);
```

If `users` has indexes on:

```text
email
age
name
created_at
status
```

the database may need to update all five indexes for the new row.

So:

```text
More indexes
     ↓
More index maintenance
     ↓
More INSERT overhead
```

---

### 2. Slower UPDATE operations

Updates can also require index maintenance.

Suppose:

```sql
UPDATE users
SET email = 'new@example.com'
WHERE id = 10;
```

If `email` is indexed, the database must update the corresponding index entry.

This becomes particularly important when frequently updated columns are indexed.

---

### 3. Slower DELETE operations

When a row is deleted, its entries must also be removed from the relevant indexes.

```sql
DELETE FROM users
WHERE id = 10;
```

Again:

```text
Delete row
   ↓
Remove corresponding index entries
```

More indexes means more work.

---

### 4. More disk space

Indexes consume additional storage.

For example:

```text
Table data       → 500 MB
Indexes          → 300 MB
--------------------------
Total            → 800 MB
```

The actual size depends heavily on the database, index type, column types, number of rows, and included/indexed columns.

Large indexes also increase backup and storage requirements.

---

### 5. More maintenance and complexity

Having many indexes makes the database harder to maintain.

You may end up with indexes that:

* are never used
* duplicate other indexes
* provide little performance benefit
* overlap with existing composite indexes

For example, having:

```sql
CREATE INDEX idx_user_id
ON orders(user_id);

CREATE INDEX idx_user_id_status
ON orders(user_id, status);
```

may make the first index unnecessary depending on the workload and database optimizer.

You should verify this rather than automatically keeping both.

---

### 6. The optimizer has more choices

When a query runs, the database optimizer considers possible execution plans.

A large number of indexes can increase the number of possible access paths it has to consider. In practice, this is usually a secondary concern compared with the **storage and write-maintenance costs**, but excessive indexing can still complicate query planning.

---

### Real-World Example

Suppose your `orders` table has:

```text
10 million rows
```

and you create indexes on:

```text
user_id
status
amount
created_at
updated_at
product_id
payment_method
city
country
```

Some of these may be useful, but if your application mostly queries:

```sql
SELECT *
FROM orders
WHERE user_id = 101
ORDER BY created_at DESC;
```

a composite index such as:

```sql
CREATE INDEX idx_orders_user_created
ON orders(user_id, created_at DESC);
```

may be more useful for that query than blindly creating many individual indexes.

The important point is to **design indexes around actual query patterns**.

### How to decide whether an index is useful

Use the query plan:

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE user_id = 101
ORDER BY created_at DESC;
```

Then check whether the index actually improves the execution plan and execution time.

### Interview Takeaway

> **Too many indexes can hurt performance because every index consumes storage and must be maintained during INSERT, UPDATE, and DELETE operations. Therefore, indexes should be created based on actual query patterns and verified using execution plans rather than indexing every column.**

A good production mindset is:

**Don't ask "Can I index this column?" → Ask "Which important queries will this index improve, and is that improvement worth its write and storage cost?**

## Answer

A many-to-many relationship exists when multiple rows in one table relate to multiple rows in another table. It is usually resolved by creating a junction table.

```sql
CREATE TABLE student_course (
    student_id INT,
    course_id INT,
    PRIMARY KEY (student_id, course_id)
);
```

### Interview takeaway

Junction tables are the standard solution for many-to-many relationships.
