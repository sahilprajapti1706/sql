## 52. What is denormalization and when might it be useful?

### Answer

**Denormalization** is the intentional introduction of **data redundancy** into a database to improve read performance, simplify queries, or support specific application workloads.

In normalization, we separate data to reduce duplication:

```text
customers
+----+-------+
| id | name  |
+----+-------+
| 1  | Rahul |
+----+-------+

orders
+----+-------------+
| id | customer_id |
+----+-------------+
| 101| 1           |
+----+-------------+
```

To display an order with the customer's name, we need a `JOIN`:

```sql
SELECT o.id, c.name
FROM orders o
JOIN customers c
  ON c.id = o.customer_id;
```

With denormalization, we might intentionally store the customer name in `orders` too:

```text
orders
+-----+-------------+---------------+
| id  | customer_id | customer_name |
+-----+-------------+---------------+
| 101 | 1           | Rahul         |
+-----+-------------+---------------+
```

Now some reads can avoid the JOIN, but the same information exists in multiple places.

---

## Why would we do this?

The main reason is:

> **Trade some storage and write complexity for faster or simpler reads.**

For example, suppose an application frequently needs:

```text
Order
  ↓
Customer
  ↓
Customer's city
  ↓
Total orders
  ↓
Latest order
```

If every request requires several JOINs and aggregations over millions of rows, carefully designed denormalization or precomputed data may reduce the work required at read time.

---

## When can denormalization be useful?

### 1. Read-heavy systems

If data is read **far more frequently than it is changed**, duplicating some information can sometimes improve performance.

For example:

```text
100,000 reads
        ↓
1,000 writes
```

It may be reasonable to optimize the read path if the consistency requirements allow it.

---

### 2. Avoiding expensive repeated JOINs

Suppose an application constantly needs:

```sql
SELECT order_id, customer_name, customer_city
FROM orders
JOIN customers ...
```

A carefully denormalized structure can store frequently needed values together.

This can reduce JOIN work, particularly in specialized workloads.

However, **denormalization should not be the first solution**. First check whether proper indexes and a better query plan solve the performance problem.

---

### 3. Reporting and analytics

Analytical workloads often involve large amounts of data and complex aggregations.

A reporting system may intentionally store:

```text
sales
customer
product
region
date
```

in a more query-friendly structure, such as a **star schema**.

This can make analytical queries easier and reduce the number of JOINs required.

---

### 4. Precomputed or cached values

Sometimes instead of calculating an expensive value every time, we store the result.

For example:

```text
products
+----+-------+--------------+
| id | name  | review_count |
+----+-------+--------------+
| 10 | Phone | 1250         |
+----+-------+--------------+
```

Instead of calculating:

```sql
SELECT COUNT(*)
FROM reviews
WHERE product_id = 10;
```

on every product-page request, the application can maintain `review_count`.

This is a form of denormalization.

The trade-off is that the stored count must remain correct.

---

## The Main Problem: Data Consistency

The biggest disadvantage is **duplicated data**.

Suppose:

```text
customers
name = 'Rahul'

orders
customer_name = 'Rahul'
```

If Rahul changes his name:

```text
customers.name → 'Rahul Sharma'
```

but `orders.customer_name` isn't updated, the database contains conflicting information.

So denormalization introduces additional responsibility:

```text
More duplicated data
        ↓
More synchronization work
        ↓
Greater consistency risk
```

---

## Normalization vs Denormalization

| Normalization                                      | Denormalization                     |
| -------------------------------------------------- | ----------------------------------- |
| Reduces duplication                                | Intentionally allows duplication    |
| Improves data consistency                          | Can increase consistency complexity |
| Usually requires more JOINs                        | Can reduce JOINs                    |
| Often better for write-heavy transactional systems | Can help read-heavy workloads       |
| Easier single source of truth                      | Requires synchronization strategy   |
| Less redundant storage                             | Potentially more storage            |

---

## Important Interview Point

Don't say:

> "Denormalization is used because JOINs are slow."

That's too simplistic.

A better answer is:

> **"Denormalization is a deliberate trade-off. It can reduce expensive reads or repeated computation in specific workloads, but it increases storage and write complexity and can introduce consistency problems."**

Before denormalizing, you should normally investigate:

```text
Slow query
    ↓
EXPLAIN ANALYZE
    ↓
Indexes?
    ↓
Query structure?
    ↓
JOIN strategy?
    ↓
Database/schema design?
    ↓
Only then consider denormalization
```

### Interview Takeaway

> **Denormalization is the intentional duplication or precomputation of data to optimize specific workloads, usually read-heavy or analytical ones. It can reduce JOINs and repeated computation, but the trade-off is extra storage, more complex writes, and potential data-consistency issue**

## Answer

A Common Table Expression (CTE) is a temporary named result set used within a query. It makes complex SQL easier to read and reason about.

```sql
WITH recent_orders AS (
    SELECT * FROM orders WHERE created_at > '2025-01-01'
)
SELECT * FROM recent_orders;
```

### Interview takeaway

CTEs help break large queries into readable logical steps without creating permanent tables.
