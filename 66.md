
## 66. How would you aggregate millions of records efficiently?

### Answer

When aggregating millions of records, the goal is to **reduce the amount of data the database has to scan, sort, join, and return**.

For example:

```sql
SELECT
    customer_id,
    SUM(amount) AS total_spent
FROM orders
GROUP BY customer_id;
```

This is logically simple, but with millions or billions of rows, performance depends heavily on how the query is designed and how the database is configured.

### 1. Filter before aggregating

If you only need recent data, filter it first:

```sql
SELECT
    customer_id,
    SUM(amount) AS total_spent
FROM orders
WHERE order_date >= DATE '2026-01-01'
GROUP BY customer_id;
```

Instead of aggregating the entire table, the database only needs to consider the relevant period.

For frequently used filters, an appropriate index can help:

```sql
CREATE INDEX idx_orders_order_date
ON orders(order_date);
```

But don't assume an index will always help; verify with the execution plan.

---

### 2. Aggregate before joining

Suppose we need total order value for each customer along with customer information.

Instead of joining millions of raw order rows:

```sql
SELECT
    c.id,
    c.name,
    SUM(o.amount)
FROM customers c
JOIN orders o
    ON o.customer_id = c.id
GROUP BY c.id, c.name;
```

we can sometimes reduce the data first:

```sql
WITH order_summary AS (
    SELECT
        customer_id,
        SUM(amount) AS total_spent
    FROM orders
    GROUP BY customer_id
)
SELECT
    c.id,
    c.name,
    COALESCE(o.total_spent, 0) AS total_spent
FROM customers c
LEFT JOIN order_summary o
    ON o.customer_id = c.id;
```

Now the join operates on **one row per customer** from the aggregated result instead of potentially millions of order rows.

---

### 3. Use the right indexes

Indexes can help with filtering and joins.

For example:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

This can be useful when queries frequently filter or join using `customer_id` and `order_date`.

However, indexes also have costs:

* Additional disk space
* Slower writes
* Index maintenance
* Possible unnecessary indexes

So I would verify the benefit using:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    customer_id,
    SUM(amount)
FROM orders
WHERE order_date >= DATE '2026-01-01'
GROUP BY customer_id;
```

---

### 4. Partition very large tables

If a table contains hundreds of millions or billions of rows, partitioning can help.

For example, partition an orders table by month:

```text
orders
├── orders_2026_01
├── orders_2026_02
├── orders_2026_03
└── ...
```

Then a query such as:

```sql
WHERE order_date >= '2026-01-01'
  AND order_date <  '2026-02-01'
```

can potentially scan only the relevant partition rather than the entire table.

This is called **partition pruning**.

Partitioning isn't automatically faster for every workload; it is most useful when the partition key aligns with common access patterns.

---

### 5. Use pre-aggregated data

If the same aggregation is requested repeatedly, don't necessarily calculate it from raw data every time.

For example, instead of repeatedly calculating:

```text
10 million orders → monthly revenue
```

maintain a summary table:

```text
monthly_revenue
-----------------------------
month       revenue
2026-01     12,500,000
2026-02     14,200,000
2026-03     13,800,000
```

Then reporting queries become much cheaper.

Depending on the database and use case, this can be implemented using:

* Summary tables
* Materialized views
* ETL/ELT pipelines
* Incremental aggregation

---

### 6. Avoid unnecessary columns

Don't use:

```sql
SELECT *
FROM orders
GROUP BY ...;
```

when you only need a few fields.

Select only the columns required for the aggregation:

```sql
SELECT
    customer_id,
    SUM(amount)
FROM orders
GROUP BY customer_id;
```

This reduces data processing and can also make execution plans simpler.

---

### 7. Avoid unnecessary `DISTINCT`

For example:

```sql
SELECT DISTINCT customer_id
FROM orders;
```

may require substantial work on a huge dataset.

If your actual requirement is aggregation, use the appropriate aggregation directly:

```sql
SELECT customer_id, COUNT(*)
FROM orders
GROUP BY customer_id;
```

The key is to understand **why** duplicates are present rather than using `DISTINCT` as a generic performance fix.

---

### 8. Process huge datasets incrementally

For extremely large datasets, I wouldn't necessarily process everything in one query or one batch.

For example:

```text
Raw data
   ↓
January batch
   ↓
February batch
   ↓
March batch
   ↓
Incremental summary
```

This reduces memory pressure and makes pipelines easier to retry and monitor.

In an ML/data-engineering environment, this could be handled through scheduled ETL/ELT jobs or distributed processing systems when a single database is no longer sufficient.

---

### 9. Check the execution plan

This is one of the most important steps.

In PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    customer_id,
    SUM(amount)
FROM orders
GROUP BY customer_id;
```

Look for things such as:

* Sequential scans
* Index scans
* Hash aggregates
* Sort operations
* Excessive disk reads
* Large differences between estimated and actual rows
* Expensive joins
* Temporary disk usage

A sequential scan is **not automatically bad**. If the query needs a large percentage of a table, scanning the table can be more efficient than repeatedly using an index.

---

### Practical strategy

For millions of records, my approach would generally be:

```text
1. Understand the required aggregation
             ↓
2. Filter unnecessary rows early
             ↓
3. Aggregate at the correct grain
             ↓
4. Aggregate before large JOINs when possible
             ↓
5. Add appropriate indexes
             ↓
6. Consider partitioning for very large tables
             ↓
7. Use pre-aggregated/materialized data for repeated reports
             ↓
8. EXPLAIN ANALYZE
             ↓
9. Measure and optimize the actual bottleneck
```

### Interview Takeaway

A strong interview answer would be:

> **For millions of records, I would filter early, aggregate at the required grain, avoid unnecessary joins and columns, use appropriate indexes, consider partitioning for very large tables, and use summary tables or materialized views for repeated aggregations. Most importantly, I would inspect `EXPLAIN ANALYZE` rather than assuming an index or optimization will help.**

The key principle is:

**Don't make the database process data that the final result doesn't need.**
