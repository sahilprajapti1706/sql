## 40. What is a transaction?

### Answer

A **transaction** is a group of one or more database operations that are treated as **one logical unit of work**.

The main idea is:

> **Either all operations succeed, or the database can undo the changes so the operation does not leave the data in an inconsistent state.**

Transactions are especially important when multiple operations depend on each other.

---

## 1. Simple Example

Consider transferring ₹1,000 from Account A to Account B.

It requires two operations:

```sql
UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;
```

Suppose the first operation succeeds but the second one fails.

Without a transaction:

```text
Account A → -₹1000
Account B → no change
```

Money has effectively disappeared.

With a transaction:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

If something goes wrong before the `COMMIT`, we can:

```sql
ROLLBACK;
```

The changes made by the transaction are undone.

---

## 2. Basic Transaction Commands

### `BEGIN`

Starts a transaction.

```sql
BEGIN;
```

### `COMMIT`

Permanently saves the transaction's changes.

```sql
COMMIT;
```

### `ROLLBACK`

Aborts the transaction and rolls back its uncommitted changes.

```sql
ROLLBACK;
```

Basic flow:

```text
BEGIN
  ↓
Operation 1
  ↓
Operation 2
  ↓
Everything successful?
  ├── Yes → COMMIT
  └── No  → ROLLBACK
```

---

## 3. ACID Properties

Transactions are commonly explained using **ACID**.

### A — Atomicity

A transaction is treated as a single unit.

> Either all required operations happen, or none of them are committed.

Example:

```text
Debit succeeds
Credit fails
    ↓
Rollback
    ↓
Neither change remains committed
```

---

### C — Consistency

A successful transaction should take the database from one **valid state** to another valid state, preserving defined constraints and rules.

For example, if a column has:

```sql
CHECK (balance >= 0)
```

the database should not end a successful transaction with a row violating that constraint.

---

### I — Isolation

When multiple transactions run concurrently, their intermediate states should not improperly interfere with one another.

For example:

```text
Transaction A → updates an order
Transaction B → reads/updates related data
```

The database's **isolation level** determines what each transaction can see from other concurrent transactions.

Common isolation levels include:

* Read Uncommitted
* Read Committed
* Repeatable Read
* Serializable

The exact behavior and supported levels depend on the database system.

---

### D — Durability

Once a transaction is successfully committed, its changes should survive failures such as a database restart.

```text
COMMIT
  ↓
Changes are durable
```

This is typically achieved using mechanisms such as transaction logs and durable storage.

---

## 4. Real-World Backend Example

Suppose an e-commerce application creates an order and decreases inventory.

You might need:

```sql
BEGIN;

INSERT INTO orders (...);

UPDATE products
SET stock = stock - 1
WHERE id = 101
  AND stock > 0;

COMMIT;
```

If the order is created but the inventory update cannot be completed correctly, the application should handle the transaction appropriately rather than leaving the database in a partially completed state.

In a Node.js backend using PostgreSQL, this typically means obtaining a database connection, running all related queries on that **same connection**, and then committing or rolling back.

Conceptually:

```text
BEGIN
  ↓
Create order
  ↓
Update inventory
  ↓
Success? ── Yes → COMMIT
  │
  No
  ↓
ROLLBACK
```

---

## 5. Transaction vs Query

A **query** is an individual database operation.

A **transaction** groups one or more operations into a single logical unit.

For example:

```text
Query 1 → INSERT order
Query 2 → UPDATE inventory
Query 3 → INSERT payment record

        ↓
     Transaction
        ↓
   COMMIT / ROLLBACK
```

Not every individual query needs an explicitly managed multi-statement transaction, but transactions are important when several changes must succeed or fail together.
