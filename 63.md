
## 63. Find users who performed a specific sequence of actions

### Answer

This is a common **event-tracking / user-behavior** problem.

Suppose we want to find users who performed this sequence:

```text
login → view_product → purchase
```

Assume an `user_events` table:

| id | user_id | action       | event_time |
| -: | ------: | ------------ | ---------- |
|  1 |     101 | login        | 10:00      |
|  2 |     101 | view_product | 10:05      |
|  3 |     101 | purchase     | 10:10      |
|  4 |     102 | login        | 11:00      |
|  5 |     102 | purchase     | 11:05      |
|  6 |     103 | login        | 12:00      |
|  7 |     103 | view_product | 12:05      |
|  8 |     103 | purchase     | 12:10      |

We want users who performed the actions **in that order**.

### Using `LEAD()`

```sql
WITH events AS (
    SELECT
        user_id,
        action,
        event_time,
        LEAD(action, 1) OVER (
            PARTITION BY user_id
            ORDER BY event_time
        ) AS next_action,
        LEAD(action, 2) OVER (
            PARTITION BY user_id
            ORDER BY event_time
        ) AS action_after_next
    FROM user_events
)
SELECT DISTINCT user_id
FROM events
WHERE action = 'login'
  AND next_action = 'view_product'
  AND action_after_next = 'purchase';
```

### How it works

For user `101`, the window function produces:

```text
login          → view_product → purchase
view_product   → purchase     → NULL
purchase       → NULL         → NULL
```

The first row matches:

```text
login → view_product → purchase
```

Therefore user `101` is returned.

User `102` does not match because:

```text
login → purchase
```

User `103` does match.

Result:

```text
user_id
-------
101
103
```

### Another approach: `LAG()`

`LAG()` is useful when you want to look **backward** instead of forward.

For example, finding the event immediately following a `login` can be handled with `LEAD()`, while identifying what happened before a `purchase` can use:

```sql
LAG(action) OVER (
    PARTITION BY user_id
    ORDER BY event_time
)
```

### Important real-world consideration

There are two different meanings of "sequence":

**1. Consecutive sequence**

```text
login → view_product → purchase
```

No other action can occur between them.

The `LEAD()` solution above checks this.

**2. Ordered sequence**

```text
login → ... → view_product → ... → purchase
```

Other actions are allowed between the required actions.

For this requirement, you need a different query, often using multiple timestamps, `EXISTS`, or a window-based approach.

### Interview Takeaway

For a fixed consecutive event sequence, remember:

```sql
LEAD(action) OVER (
    PARTITION BY user_id
    ORDER BY event_time
)
```

The general pattern is:

**Partition events by user → order by time → use `LEAD()`/`LAG()` → check the required sequence.**
