## 4. What are primary keys and foreign keys?

### Answer

**Primary keys and foreign keys are used to identify records and establish relationships between tables in a relational database.**

* **Primary Key (PK)** → Uniquely identifies each row in a table.
* **Foreign Key (FK)** → Creates a relationship by referencing a key, usually the primary key, in another table.

A simple way to remember:

```text
Primary Key  → "Who is this record?"
Foreign Key  → "Which record is this related to?"
```

---

## 1. Primary Key

A **primary key** is a column or combination of columns whose value uniquely identifies each row in a table.

Example:

```text
users
+----+--------+-------------------+
| id | name   | email             |
+----+--------+-------------------+
| 1  | Sahil  | sahil@example.com  |
| 2  | Rahul  | rahul@example.com  |
| 3  | Priya  | priya@example.com  |
+----+--------+-------------------+
```

Here, `id` can be the primary key:

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255)
);
```

### Properties of a primary key

A primary key must:

* Uniquely identify a row.
* Not contain `NULL` values.
* Have only one primary-key constraint per table, although that constraint can contain multiple columns.

For example, two users cannot both have:

```text
id = 1
```

### Why do we need a primary key?

Without a reliable unique identifier, it becomes difficult to precisely identify or update a particular record.

For example:

```sql
UPDATE users
SET email = 'new@example.com'
WHERE id = 2;
```

The primary key `id = 2` identifies the intended user.

---

# 2. Foreign Key

A **foreign key** is a column or set of columns in one table that references a candidate key—commonly the primary key—of another table.

Suppose we have:

```text
users
+----+--------+
| id | name   |
+----+--------+
| 1  | Sahil  |
| 2  | Rahul  |
+----+--------+
```

And:

```text
orders
+----+---------+--------+
| id | user_id | amount |
+----+---------+--------+
| 101| 1       | 500    |
| 102| 1       | 800    |
| 103| 2       | 300    |
+----+---------+--------+
```

Here:

```text
orders.user_id → users.id
```

`orders.user_id` can be defined as a foreign key:

```sql
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    user_id INTEGER,
    amount DECIMAL(10, 2),

    FOREIGN KEY (user_id)
        REFERENCES users(id)
);
```

Now the database knows that an order's `user_id` should refer to an existing user (subject to the foreign-key actions and constraints configured).

---

## Why do we need foreign keys?

The main purpose is to maintain **referential integrity**.

For example, if `users.id = 1` does not exist, the database can prevent inserting an order referring to user `1`.

This helps prevent invalid relationships such as:

```text
orders
user_id = 9999

but

users
id = 9999   ← doesn't exist
```

Without appropriate constraints, the application could end up with an order belonging to a nonexistent user.

---

## Primary Key vs Foreign Key

| Aspect                    | Primary Key                   | Foreign Key                          |
| ------------------------- | ----------------------------- | ------------------------------------ |
| Purpose                   | Identifies a row              | Establishes a relationship           |
| Uniqueness                | Must uniquely identify rows   | Does not generally need to be unique |
| `NULL`                    | Not allowed                   | May be allowed depending on schema   |
| Where defined             | In the table being identified | In the referencing table             |
| References another table? | Not necessarily               | Yes                                  |
| Example                   | `users.id`                    | `orders.user_id`                     |

### Important point

A foreign key **does not have to reference a primary key specifically**. In relational databases such as PostgreSQL, it can reference a suitable **unique/candidate key** as permitted by the database.

For placement interviews, however, the common pattern is:

```text
orders.user_id → users.id (Primary Key)
```

## How they work together

Consider an e-commerce system:

```text
users
┌──────────────┐
│ id (PK)      │
│ name         │
└──────┬───────┘
       │
       │ referenced by
       ↓
orders
┌──────────────────┐
│ id (PK)          │
│ user_id (FK)     │
│ amount           │
└──────────────────┘
```

The relationship can be represented as:

```text
users.id  ───────────<  orders.user_id
```

One user can have multiple orders.

This is a **one-to-many relationship**:

```text
One User
   ↓
Many Orders
```

---

## Practical Example: JOIN

Once the tables are related, we can retrieve information from both tables:

```sql
SELECT
    users.name,
    orders.amount
FROM users
JOIN orders
    ON users.id = orders.user_id;
```

Possible result:

```text
name   | amount
-------|-------
Sahil  | 500
Sahil  | 800
Rahul  | 300
```

The foreign key provides the logical connection that allows these records to be related.

## What happens when a referenced record is deleted?

This is an important interview follow-up.

Suppose user `1` has orders and we try to delete that user.

The database can be configured with different foreign-key actions, such as:

* `RESTRICT` / `NO ACTION` → prevent the deletion when dependent rows exist.
* `CASCADE` → delete the related child rows.
* `SET NULL` → set the foreign-key value to `NULL`, if allowed.

Example:

```sql
FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE CASCADE
```

With `CASCADE`, deleting a user can also delete that user's related orders.

**This behavior should be chosen carefully**, because cascading deletion can remove significant amounts of data.

---

## Composite Keys

A key does not always have to be a single column.

For example, in a course-enrollment system:

```text
student_id
course_id
```

Together they could uniquely identify an enrollment:

```sql
PRIMARY KEY (student_id, course_id)
```

This is called a **composite primary key**.

The same idea can apply to composite foreign keys.

---

## Common Mistakes

### 1. Assuming every foreign key must be unique

Not true.

A user can have many orders:

```text
orders.user_id
1
1
1
2
```

So multiple rows can contain the same foreign-key value.

### 2. Thinking a primary key must be an `id` column

Not necessarily. A primary key can be based on any suitable column or combination of columns that uniquely identifies records.

### 3. Thinking foreign keys are only for JOINs

Foreign keys are also important for **enforcing referential integrity** and preventing invalid relationships.

### 4. Confusing primary key with unique constraint

Both can enforce uniqueness, but a table has one primary-key constraint, and the primary key serves as the table's principal row identifier. A table can have multiple `UNIQUE` constraints.

---

## Interview Takeaway

Remember:

```text
Primary Key
    ↓
Uniquely identifies a row

Foreign Key
    ↓
References a key in another table
    ↓
Establishes/enforces a relationship
```

A strong interview answer would be:

> **A primary key uniquely identifies each record in a table, while a foreign key references a key in another table to establish a relationship and maintain referential integrity. For example, `users.id` can be a primary key, while `orders.user_id` can be a foreign key referencing `users.id`.**
