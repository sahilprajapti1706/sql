## 44. What is an index?

### Answer

An **index** is a database data structure that helps the database **find rows faster** without scanning the entire table.

Think of it like the **index of a book**.

Without an index, if you want to find all employees with a particular email, the database may need to check many rows:

```text
Row 1 → check
Row 2 → check
Row 3 → check
...
Row 1,000,000 → check
```

With an appropriate index, the database can locate the relevant rows much more efficiently.

---

## 1. Creating an Index

Suppose we frequently search users by email:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Now a query such as:

```sql
SELECT *
FROM users
WHERE email = 'sahil@example.com';
```

can potentially use that index instead of scanning the entire table.

The database optimizer decides whether the index is actually beneficial.

---

## 2. How an Index Works

A common index structure is a **B-tree**.

Conceptually:

```text
             Index
               |
        ┌──────┴──────┐
       50             100
      /  \            /  \
    20   40          70   120
```

Instead of checking every row, the database can navigate the index to locate the relevant key and then find the corresponding table row(s).

This is why indexes can significantly improve queries involving:

* `WHERE`
* `JOIN`
* `ORDER BY`
* sometimes `GROUP BY`

depending on the index structure and query.

---

## 3. Indexes Improve Reads but Have a Cost

Indexes are **not free**.

### Without an index

```text
INSERT → write table
UPDATE → write table
DELETE → write table
```

### With an index

```text
INSERT → update table + update index
UPDATE → update table + possibly update index
DELETE → update table + update index
```

Therefore, indexes can:

* Improve read/query performance
* Consume additional disk space
* Add overhead to `INSERT`, `UPDATE`, and `DELETE`
* Require maintenance

So you should not automatically index every column.

---

## 4. Primary Keys and Indexes

When you define:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name TEXT
);
```

the database generally creates an index to enforce the primary-key uniqueness constraint.

The exact implementation is database-specific, but in PostgreSQL a primary key automatically creates a unique B-tree index.

Similarly, a `UNIQUE` constraint is generally backed by a unique index in PostgreSQL.

---

## 5. Composite Index

You can create an index on multiple columns:

```sql
CREATE INDEX idx_orders_user_status
ON orders(user_id, status);
```

This can be useful for queries such as:

```sql
SELECT *
FROM orders
WHERE user_id = 101
  AND status = 'completed';
```

### Important: column order matters

For a composite index:

```sql
(user_id, status)
```

the order of the columns affects which queries can efficiently use the index.

A common mental model for a B-tree composite index is the **leftmost prefix**:

```text
(user_id, status)
```

is naturally useful for queries filtering by:

```text
user_id
```

or:

```text
user_id + status
```

but may not be as useful for a query filtering only by:

```text
status
```

---

## 6. Indexes and `EXPLAIN`

You should not assume an index will always make a query faster.

The database optimizer considers factors such as:

* Number of rows
* Selectivity of the condition
* Cost of reading the index
* Cost of fetching table rows
* Available indexes
* Query structure

You can inspect the query plan using:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'sahil@example.com';
```

This helps determine whether the database actually used the index and whether the query improved.

---

## 7. Example from a Backend Application

Suppose an API frequently does:

```sql
SELECT *
FROM listings
WHERE owner_id = $1;
```

If `owner_id` is frequently used for filtering and the table is large, an index may be appropriate:

```sql
CREATE INDEX idx_listings_owner_id
ON listings(owner_id);
```

Now the database has a structure specifically designed to make lookups by `owner_id` more efficient.

---

### Interview Takeaway

Remember:

> **An index is an additional data structure that helps the database locate and access rows efficiently.**

But also remember the trade-off:

> **Indexes speed up suitable reads, but consume storage and can add overhead to writes.**

A strong interview answer should mention that **indexes should be created based on actual query patterns and verified with `EXPLAIN`/`EXPLAIN ANALYZE`, rather than indexing every column**
