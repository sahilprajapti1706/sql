
## 50. How would you troubleshoot a slow SQL query?

### Answer

I would **measure first, identify the bottleneck, make one targeted change, and measure again**.

A slow query is not automatically an indexing problem. It could be caused by a bad execution plan, inefficient JOINs, too many rows being processed, sorting, missing indexes, stale statistics, locks, or even database/resource contention.

### 1. Reproduce and measure the problem

First, run the exact query with representative parameters and determine:

* How long does it take?
* Is it consistently slow or only sometimes?
* How many rows does it process and return?
* Did performance recently change?

In PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE user_id = 101;
```

`EXPLAIN ANALYZE` is particularly useful because it shows **actual execution behavior**, while `BUFFERS` provides information about data pages read from or found in cache.

---

### 2. Read the execution plan

Look for expensive operations such as:

```text
Sequential Scan
Sort
Nested Loop
Hash Join
Aggregate
```

For example:

```text
Seq Scan on orders
  actual rows=10000000
```

If the query is processing millions of rows when only a few are needed, that's something worth investigating.

Don't assume a sequential scan is always bad. If a query needs a large percentage of a table, scanning the table can legitimately be cheaper than using an index.

---

### 3. Check indexes

Ask:

> Does the query have an appropriate index for its filtering, JOIN, or ordering pattern?

For example:

```sql
SELECT *
FROM orders
WHERE user_id = 101
ORDER BY created_at DESC;
```

An index such as:

```sql
CREATE INDEX idx_orders_user_created
ON orders(user_id, created_at DESC);
```

may be useful because the query filters by `user_id` and then orders by `created_at`.

But don't blindly add indexes. Indexes increase storage and write-maintenance costs.

---

### 4. Check JOINs

JOINs can become expensive when large tables are joined inefficiently.

For example:

```sql
SELECT *
FROM orders o
JOIN users u
  ON u.id = o.user_id
WHERE u.country = 'India';
```

I would inspect:

* Are the JOIN columns appropriately indexed?
* Are unnecessary rows being joined?
* Is the JOIN type correct?
* Is a one-to-many relationship unexpectedly multiplying rows?

---

### 5. Check how many rows are processed

A query might return only:

```text
100 rows
```

but internally process:

```text
5,000,000 rows
```

That can be a major performance problem.

For example, avoid retrieving unnecessary data:

```sql
SELECT *
FROM orders;
```

when the application only needs:

```sql
SELECT id, amount, created_at
FROM orders;
```

However, selecting fewer columns alone doesn't guarantee a major improvement; the execution plan and I/O pattern matter.

---

### 6. Check filtering and sorting

Look for expensive operations such as:

```sql
ORDER BY
GROUP BY
DISTINCT
```

especially when they operate on a large intermediate result.

For example:

```sql
SELECT *
FROM orders
WHERE status = 'completed'
ORDER BY created_at DESC
LIMIT 20;
```

An appropriate index may allow the database to find the required rows in the desired order without sorting a huge result set.

---

### 7. Check statistics and data distribution

The optimizer relies on statistics to estimate things like:

```text
How many rows will this condition return?
How selective is this column?
Which execution strategy is likely to be cheaper?
```

If estimates are significantly different from actual results, investigate statistics.

In PostgreSQL, for example:

```sql
ANALYZE orders;
```

can update table statistics.

A large difference such as:

```text
estimated rows = 100
actual rows    = 500000
```

can help explain why the optimizer selected a poor plan.

---

### 8. Check for locks and database contention

Sometimes the query itself is fine but is **waiting for another transaction**.

For example:

```text
Query
  ↓
Waiting for lock
  ↓
Another transaction hasn't committed
```

In production, I would therefore also check:

* active transactions
* blocking queries
* lock waits
* CPU usage
* memory pressure
* disk I/O
* connection pool exhaustion

This is especially important when a query is normally fast but suddenly becomes slow.

---

### 9. Check the application layer

The database may not actually be the bottleneck.

For example:

```text
API request
   ↓
Database query: 50 ms
   ↓
Application processing: 500 ms
   ↓
Network: 100 ms
```

The user experiences a slow request, but optimizing the SQL query would not solve the main problem.

For an application using Node.js and PostgreSQL, I would also check query timing, connection-pool behavior, and whether multiple unnecessary queries are being executed.

---

### 10. Optimize one thing at a time and re-test

After identifying the bottleneck, make a targeted change:

```text
Measure
  ↓
EXPLAIN ANALYZE
  ↓
Identify bottleneck
  ↓
Change query/index/schema
  ↓
EXPLAIN ANALYZE again
  ↓
Compare results
```

Don't make five changes simultaneously because then it becomes difficult to know which change actually helped.

---

### Practical Troubleshooting Example

Suppose this query is slow:

```sql
SELECT *
FROM orders
WHERE user_id = 101
ORDER BY created_at DESC
LIMIT 20;
```

I would start with:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE user_id = 101
ORDER BY created_at DESC
LIMIT 20;
```

If the plan shows a large sequential scan followed by an expensive sort, I would investigate an index such as:

```sql
CREATE INDEX idx_orders_user_created
ON orders(user_id, created_at DESC);
```

Then run the query again and compare the execution plan and actual performance.

The goal isn't simply **"add an index."**

The goal is:

> **Understand why the database chose the current plan, identify the actual bottleneck, make the smallest appropriate change, and verify the improvement with measurements.**

### Common Mistakes

* Adding indexes to every column without checking query patterns.
* Assuming every sequential scan is bad.
* Optimizing based only on intuition instead of `EXPLAIN ANALYZE`.
* Looking only at the SQL and ignoring locks, I/O, CPU, or connection-pool issues.
* Making multiple changes at once and then not knowing what fixed the problem.
* Testing with tiny development data when production contains millions of rows.

### Interview Takeaway

> **To troubleshoot a slow SQL query, I would reproduce and measure it, inspect the execution plan using `EXPLAIN ANALYZE`, check indexes, JOINs, filtering, sorting, row estimates, and statistics, then investigate locks and database resources if necessary. After making a targeted optimization, I would run the query again and compare the actual execution metrics.**
