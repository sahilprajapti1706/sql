
## 67. How would you perform feature aggregation using SQL?

### Answer

**Feature aggregation** means converting raw records into useful numerical features that can be used for **ML models, analytics, or reporting**.

For example, instead of giving a model 100 individual orders for a customer, we can create features such as:

* Total orders
* Total amount spent
* Average order value
* Maximum order value
* Number of distinct products
* Number of orders in the last 30 days

### Example

Suppose we have an `orders` table:

```text
orders
-----------------------------------------
order_id | customer_id | amount | date
```

We can create customer-level features using `GROUP BY`:

```sql
SELECT
    customer_id,
    COUNT(*) AS total_orders,
    SUM(amount) AS total_spent,
    AVG(amount) AS avg_order_value,
    MAX(amount) AS max_order_value,
    MIN(amount) AS min_order_value
FROM orders
GROUP BY customer_id;
```

Now instead of many order-level records, we get **one feature row per customer**.

---

### Adding more useful features

Suppose orders also contain `product_id` and `status`:

```sql
SELECT
    customer_id,
    COUNT(*) AS total_orders,
    COUNT(DISTINCT product_id) AS unique_products,
    SUM(amount) AS total_spent,
    AVG(amount) AS avg_order_value,
    MAX(amount) AS max_order_value,
    SUM(
        CASE
            WHEN status = 'completed' THEN amount
            ELSE 0
        END
    ) AS completed_revenue
FROM orders
GROUP BY customer_id;
```

This produces features such as:

| customer_id | total_orders | unique_products | total_spent | avg_order_value |
| ----------: | -----------: | --------------: | ----------: | --------------: |
|         101 |           12 |               8 |      45,000 |           3,750 |
|         102 |            5 |               4 |      18,000 |           3,600 |

---

### Time-based feature aggregation

For ML, we often need features from a specific time window.

For example, **number of orders in the last 30 days**:

```sql
SELECT
    customer_id,
    COUNT(*) AS orders_last_30_days,
    SUM(amount) AS spent_last_30_days,
    AVG(amount) AS avg_order_value_last_30_days
FROM orders
WHERE order_date >= CURRENT_DATE - INTERVAL '30 days'
GROUP BY customer_id;
```

This is more useful for many prediction problems than aggregating the customer's entire history.

---

### Combining multiple tables

Suppose we also have a `customer_activity` table:

```text
customer_activity
--------------------------------
customer_id | login_count | views
```

We can create features from both sources:

```sql
WITH order_features AS (
    SELECT
        customer_id,
        COUNT(*) AS total_orders,
        SUM(amount) AS total_spent,
        AVG(amount) AS avg_order_value
    FROM orders
    GROUP BY customer_id
),
activity_features AS (
    SELECT
        customer_id,
        SUM(login_count) AS total_logins,
        SUM(views) AS total_views
    FROM customer_activity
    GROUP BY customer_id
)
SELECT
    c.customer_id,
    COALESCE(o.total_orders, 0) AS total_orders,
    COALESCE(o.total_spent, 0) AS total_spent,
    COALESCE(o.avg_order_value, 0) AS avg_order_value,
    COALESCE(a.total_logins, 0) AS total_logins,
    COALESCE(a.total_views, 0) AS total_views
FROM customers c
LEFT JOIN order_features o
    ON o.customer_id = c.customer_id
LEFT JOIN activity_features a
    ON a.customer_id = c.customer_id;
```

This is often safer than joining the raw `orders` and `customer_activity` tables directly because both may contain **multiple rows per customer**.

---

### Important: Define the grain

Before creating features, decide what **one row represents**.

For example:

```text
One row = one customer
```

Then every feature should ultimately be aggregated to:

```text
customer_id → one row
```

For a time-series model, it might instead be:

```text
One row = one customer per month
```

Then:

```sql
SELECT
    customer_id,
    DATE_TRUNC('month', order_date) AS month,
    COUNT(*) AS order_count,
    SUM(amount) AS monthly_spend
FROM orders
GROUP BY
    customer_id,
    DATE_TRUNC('month', order_date);
```

---

### Avoiding data leakage

For ML feature engineering, aggregation must respect the **prediction time**.

For example, if you're predicting whether a customer will purchase in April:

```text
January ───── February ───── March | April
             Features              | Target
```

Features should be calculated using data available **before April**.

You should not accidentally include April orders in:

```sql
SUM(amount)
```

because that would give the model information from the future.

---

### Common aggregation functions

| Function            | Example feature                    |
| ------------------- | ---------------------------------- |
| `COUNT()`         | Number of orders                   |
| `COUNT(DISTINCT)` | Number of unique products          |
| `SUM()`           | Total spending                     |
| `AVG()`           | Average order value                |
| `MIN()`           | Minimum purchase                   |
| `MAX()`           | Maximum purchase                   |
| `CASE + SUM()`    | Number/amount matching a condition |

### Interview Takeaway

A strong interview answer is:

> **I would first define the grain of the training dataset, such as one row per customer. Then I would use `GROUP BY` with aggregate functions like `COUNT`, `SUM`, `AVG`, `MIN`, and `MAX` to convert raw transactional data into features. For multiple tables, I would usually aggregate each one to the required grain before joining them, which prevents row multiplication. For ML, I would also apply the correct time window and ensure that features only use information available before the prediction point.**

The key pattern is:

**Raw records → filter → aggregate → one row per entity → feature dataset.**
