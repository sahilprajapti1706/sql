
## 64. How would you extract training data from multiple relational tables?

### Answer

When preparing **training data for an ML model**, the data is often spread across multiple relational tables.

The general process is:

```text
Relational tables
      ↓
JOIN related data
      ↓
Filter relevant records
      ↓
Aggregate / transform features
      ↓
Create target/label
      ↓
Validate data
      ↓
Export training dataset
```

### Example

Suppose we have an e-commerce database:

**customers**

| customer_id | age | city   |
| ----------: | --: | ------ |
|           1 |  25 | Delhi  |
|           2 |  32 | Mumbai |

**orders**

| order_id | customer_id | order_date | amount |
| -------: | ----------: | ---------- | -----: |
|      101 |           1 | 2026-01-10 |   5000 |
|      102 |           1 | 2026-02-15 |   3000 |
|      103 |           2 | 2026-02-20 |   7000 |

**customer_activity**

| customer_id | login_count | product_views |
| ----------: | ----------: | ------------: |
|           1 |          20 |            50 |
|           2 |          10 |            30 |

Suppose we want training data to predict whether a customer will make a purchase.

We can combine these tables:

```sql
SELECT
    c.customer_id,
    c.age,
    c.city,
    COUNT(o.order_id) AS order_count,
    COALESCE(SUM(o.amount), 0) AS total_spent,
    COALESCE(a.login_count, 0) AS login_count,
    COALESCE(a.product_views, 0) AS product_views
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.customer_id
LEFT JOIN customer_activity a
    ON a.customer_id = c.customer_id
GROUP BY
    c.customer_id,
    c.age,
    c.city,
    a.login_count,
    a.product_views;
```

This produces a **feature dataset** where each row represents a customer.

### Why use `LEFT JOIN`?

If a customer has never placed an order, we still want that customer in the training dataset.

For example:

```text
Customer 1 → 2 orders
Customer 2 → 1 order
Customer 3 → 0 orders
```

An `INNER JOIN` would remove Customer 3.

A `LEFT JOIN` keeps Customer 3 and we can convert the missing aggregate to `0` using:

```sql
COALESCE(SUM(o.amount), 0)
```

---

### Creating the target variable

For supervised learning, we also need a **label/target**.

For example:

> Predict whether the customer will purchase in the next 30 days.

We might create:

```sql
CASE
    WHEN COUNT(o.order_id) > 0 THEN 1
    ELSE 0
END AS purchased
```

In a real ML pipeline, however, the label should be defined using a **future time window**, while features should come only from data available before the prediction time.

This is extremely important because otherwise we can introduce **data leakage**.

---

### Avoiding data leakage

Suppose we are predicting whether a customer will purchase in March.

We should build features using information available **before March**:

```text
Historical data              Prediction period
      │                             │
      ▼                             ▼
Jan ─────── Feb ─────── | ─────── March
       Features          |          Label
```

Do **not** accidentally use March purchase information as an input feature.

For example:

```text
❌ total_spent including March purchases
```

could leak the answer into the model.

Instead:

```text
✅ total_spent up to February 28
```

---

### Production approach

For a real ML system, I would generally:

1. **Identify the prediction target** and prediction time.
2. Identify the relevant relational tables.
3. Define the relationships and join keys.
4. Use SQL to join and aggregate the raw data.
5. Create meaningful features.
6. Generate labels using the appropriate future window.
7. Prevent data leakage.
8. Handle `NULL`, duplicates, and missing records.
9. Validate row counts and feature distributions.
10. Export the resulting dataset to a data warehouse, Parquet/CSV, or directly into the training pipeline.

### Important issue: duplicate rows after JOINs

Suppose one customer has:

```text
5 orders
10 activity records
```

A careless join can produce:

```text
5 × 10 = 50 rows
```

instead of one customer-level record.

Therefore, for ML datasets, you need to understand the **cardinality of every relationship** and often aggregate each one-to-many table before joining.

For example:

```sql
WITH order_features AS (
    SELECT
        customer_id,
        COUNT(*) AS order_count,
        SUM(amount) AS total_spent
    FROM orders
    GROUP BY customer_id
)
SELECT
    c.customer_id,
    c.age,
    c.city,
    COALESCE(o.order_count, 0) AS order_count,
    COALESCE(o.total_spent, 0) AS total_spent
FROM customers c
LEFT JOIN order_features o
    ON c.customer_id = o.customer_id;
```

This is often safer than joining raw one-to-many tables directly.

### Interview Takeaway

The core approach is:

> **Join related tables using their keys, aggregate one-to-many data to the required grain, create features and labels, and carefully prevent duplicate rows and data leakage.**

For ML, the most important question is not just **"How do I JOIN the tables?"**, but also:

**"What should one row of my training dataset represent?"**

For example:

```text
One row = one customer
One row = one transaction
One row = one listing
One row = one day per customer
```

Once the **grain of the training dataset** is defined, the joins and aggregations become much easier to design correctly.
