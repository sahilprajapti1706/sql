## 29. What is a recursive CTE and where can it be useful?

### Answer

A **recursive CTE** is a CTE that **references itself** to repeatedly process data until there are no more rows to process or a stopping condition is reached.

It is defined using:

```sql
WITH RECURSIVE
```

Recursive CTEs are particularly useful for **hierarchical or tree-structured data**, where one row points to another row in the same table.

Common examples:

* Employee → Manager hierarchies
* Category → Subcategory
* Folder → Subfolder
* Organization structures
* Bill of materials
* Graph/tree traversal

---

## Basic Structure

A recursive CTE usually has two parts:

```sql
WITH RECURSIVE cte_name AS (

    -- 1. Anchor query
    SELECT ...

    UNION ALL

    -- 2. Recursive query
    SELECT ...
    FROM ...
    JOIN cte_name ...
)
SELECT *
FROM cte_name;
```

### The two important parts

**1. Anchor query**

Provides the starting rows.

**2. Recursive query**

Uses the rows already produced by the CTE to find the next level.

Conceptually:

```text
Start
  ↓
Level 1
  ↓
Level 2
  ↓
Level 3
  ↓
...
  ↓
No more matching rows
```

## Example: Employee Hierarchy

Suppose we have:

| id | name  | manager_id |
| -: | ----- | ---------: |
|  1 | Raj   |       NULL |
|  2 | Sahil |          1 |
|  3 | Rahul |          1 |
|  4 | Priya |          2 |
|  5 | Amit  |          2 |

Here:

```text
Raj
├── Sahil
│   ├── Priya
│   └── Amit
└── Rahul
```

We can use a recursive CTE to retrieve the entire hierarchy starting from Raj.

```sql
WITH RECURSIVE employee_tree AS (

    -- Anchor: start with the top-level employee
    SELECT
        id,
        name,
        manager_id,
        1 AS level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive: find employees managed by the current level
    SELECT
        e.id,
        e.name,
        e.manager_id,
        et.level + 1
    FROM employees e
    JOIN employee_tree et
        ON e.manager_id = et.id
)

SELECT *
FROM employee_tree
ORDER BY level, id;
```

Result:

| id | name  | manager_id | level |
| -: | ----- | ---------: | ----: |
|  1 | Raj   |       NULL |     1 |
|  2 | Sahil |          1 |     2 |
|  3 | Rahul |          1 |     2 |
|  4 | Priya |          2 |     3 |
|  5 | Amit  |          2 |     3 |

The recursive part repeatedly finds employees whose `manager_id` matches an employee already found.

---

## How the recursion works

Think about it step by step.

### First iteration

The anchor query finds:

```text
Raj
```

### Second iteration

The recursive query finds employees whose manager is Raj:

```text
Sahil
Rahul
```

### Third iteration

It finds employees whose manager is Sahil:

```text
Priya
Amit
```

### Next iteration

If there are no more employees under them, recursion stops.

So:

```text
Raj
 ↓
Sahil, Rahul
 ↓
Priya, Amit
 ↓
No more employees
```

## Another Common Example: Categories

Suppose an e-commerce system has:

| id | name           | parent_id |
| -: | -------------- | --------: |
|  1 | Electronics    |      NULL |
|  2 | Computers      |         1 |
|  3 | Laptops        |         2 |
|  4 | Gaming Laptops |         3 |

A recursive CTE can retrieve all descendants of `Electronics`.

```sql
WITH RECURSIVE category_tree AS (

    SELECT id, name, parent_id
    FROM categories
    WHERE id = 1

    UNION ALL

    SELECT
        c.id,
        c.name,
        c.parent_id
    FROM categories c
    JOIN category_tree ct
        ON c.parent_id = ct.id
)

SELECT *
FROM category_tree;
```

This follows:

```text
Electronics
    ↓
Computers
    ↓
Laptops
    ↓
Gaming Laptops
```

## Recursive CTE vs Normal CTE

A normal CTE does not reference itself:

```sql
WITH recent_orders AS (
    SELECT *
    FROM orders
    WHERE order_date >= CURRENT_DATE - INTERVAL '30 days'
)
SELECT *
FROM recent_orders;
```

A recursive CTE references itself:

```sql
WITH RECURSIVE employee_tree AS (
    ...
    UNION ALL
    SELECT ...
    FROM employee_tree
)
SELECT *
FROM employee_tree;
```

| Normal CTE                            | Recursive CTE                        |
| ------------------------------------- | ------------------------------------ |
| Does not reference itself             | References itself                    |
| Usually represents a fixed query step | Processes data iteratively           |
| Good for organizing complex queries   | Good for hierarchical/recursive data |
| Uses`WITH`                          | Uses`WITH RECURSIVE`               |

---

## Important: Preventing Infinite Recursion

A recursive CTE needs a way for recursion to **eventually stop**.

Normally, this happens naturally when the recursive query finds no more matching rows.

But bad data can create cycles, such as:

```text
Employee A → Employee B
Employee B → Employee A
```

In such cases, recursion can continue indefinitely unless you explicitly prevent cycles or impose a limit.

For production systems, hierarchical data should therefore have appropriate validation and cycle-handling logic.

---

## Where is it useful?

Recursive CTEs are especially useful when the number of hierarchy levels is **not known in advance**.

For example, you don't know whether a category has:

```text
2 levels
```

or:

```text
10 levels
```

or:

```text
50 levels
```

Instead of writing separate queries for each level, recursion handles the hierarchy dynamically.

### Interview Takeaway

> **A recursive CTE is a CTE that references itself, allowing SQL to repeatedly traverse hierarchical or recursive data until the recursive condition produces no more rows.**

Remember the structure:

```text
WITH RECURSIVE
      ↓
Anchor query
      ↓
UNION ALL
      ↓
Recursive query
      ↓
Repeat until no more rows
```

If the data looks like **parent → child → grandchild → ...**, a recursive CTE is a strong SQL tool to conside
